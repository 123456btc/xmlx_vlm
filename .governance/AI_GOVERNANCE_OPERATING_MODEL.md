# AI Governance Operating Model — 四驱研发模式与风险分级

> **生产实施说明**：本操作模型定义了 `xmlx_vlm` 体系中 AI 协同开发的四种强制驱动模式与风险分级门禁。

---

## 一、 为什么需要治理操作模型？

在由大模型协助完成的代码开发中，常见的失败模式包括：
* 没有设计边界直接开始写代码；
* 仅编写 happy path 测试，缺失边界与异常注入；
* 修改局部逻辑引发未知组件崩溃（未评估爆炸半径）；
* 同一个历史 Bug 换个 Prompt 再次被大模型犯一遍。

本模型将治理准则转化为**确凿的提交证据与门禁校验**。

---

## 二、 四大强制研发驱动模式

### 1. SDD (Software Design Driven — 设计驱动)
* **要求**：在对高危模块进行修改前，必须明确设计边界。
* **交付要素**：
  * 责任组件与治理层级；
  * 数据流向与持久化节点；
  * 状态机流转图（State Transitions）或明确“无生命周期状态”；
  * 异常降级模式与回滚策略。

### 2. TDD (Test Driven Development — 测试驱动)
* **要求**：**先写失败用例，再写生产代码，使之变绿。**
* **铁律**：未运行失败测试而直接写成的生产代码，一律物理删除。
* **交付要素**：
  * 显式指出在实现前失败的测试用例；
  * 覆盖 Happy Path 以及边界值、超时、数据损坏、重复重放等异常场景；
  * PR 中必须粘贴真实终端执行输出。

### 3. CDD (Contract & Callgraph Driven — 契约与调用图谱驱动)
* **要求**：在修改涉及公共接口或热路径的代码前，必须明确接口契约与调用者。
* **交付要素**：
  * 接口输入输出契约定义（Pydantic Schema / Typed Dict）；
  * 梳理受影响的调用方（Callers）与潜在爆炸半径（Blast Radius）。

### 4. MDD (Memory / Model Driven — 大脑记忆驱动)
* **要求**：每一次故障排查与新引入的安全不变量，必须沉淀为可被模型记忆并免疫的规则。
* **交付要素**：
  * 遇到典型 Bug 后，必须将故障根因归档到 `PROJECT_BUGS_POSTMORTEM.md`；
  * 提炼对应的负向约束（Negative Constraint），同步更新 Agent Core 规则库。

## 三、 风险分级矩阵 (Risk Tiering Matrix)

| 风险级别 | 涉及代码范围 | 强制设计要求 | CI 门禁等级 |
| :--- | :--- | :--- | :--- |
| **High (高危)** | OMS 订单核心、KMS 私钥/钱包、实时执行、资金核算、风控熔断 | 强制 SDD + 严格 TDD + 爆炸半径评估 | `--full` (全量验证) |
| **Medium (中度)** | 单一指标模块、非热路径 Bug 修复、内部 CLI 工具 | 明确契约 + 单元测试覆盖 | `--scope <paths>` (范围验证) |
| **Light (低危)** | 文档修改、只读查询、页面样式微调 | 简单功能测试验证 | `--quick` (极速验证) |
